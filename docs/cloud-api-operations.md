# Cloud API: deploy, reliability and growth notes

What the `api-hill-climb` branch changes about running the cloud API, what a deploy needs, what is tied to Railway, and the recommendation for a free starter allowance. Nothing here has been deployed.

## Deploy order

1. **Migrate first.** `0009_api_dx` adds the `webhook_secrets` table, and nullable columns and two indexes to `cloud_jobs` (idempotency key and request hash, `source_url`, webhook delivery state). convt-server and convt-worker refuse to start until the database has every migration they were built with, so run `bun run db:migrate` against production before the new images roll out. The old server keeps running on the migrated database, which keeps the window between migrating and deploying safe. Do not roll convt-api back to an image from before this branch once customers use `Idempotency-Key`: the old API ignores the header, so a replayed create would reserve, and can bill, a second job. Roll back only to an image from this branch or later; if that is impossible, stop new creates (scale convt-api to zero) instead. The migration sets `lock_timeout = 5s`, so if a long transaction holds `cloud_jobs` it fails fast instead of stalling the queue; rerun it. Once it has the lock, the migration also builds its two indexes inside that lock, which blocks the queue for as long as the builds take. Both are partial and small on a young table; measure `select count(*) from cloud_jobs` first, and if it is in the millions, run the migration in a quiet window.
2. **Set `CONVT_WEBHOOK_SECRET`** (at least 32 random characters) on convt-api. Without it the API starts, refuses `webhook_url` with `400 webhooks_unavailable`, and logs a warning. Rotating it changes every account's webhook signing secret at once; a single account rotates its own with `POST /v1/webhooks/secret/rotate`.
3. **Roll the worker.** Production's worker is not on Railway: it is the Docker container `convt-worker-prod-1` on ms-a2, because Railway failed the sandbox gate (`docs/p9-cloud-plan.md`). Rebuild its image from this branch and recreate the container with the same environment plus `--stop-timeout 30`. Docker's default stop timeout is 10 seconds, shorter than the worker's 20-second shutdown grace, so without it `docker stop` kills a busy worker before it can hand its job back. Check the running revision (`docker inspect convt-worker-prod-1`) before going on.
4. **Deploy convt-api on Railway.** It refuses `source_url` with `400 source_url_unavailable` until step 5, so the old worker can never be handed a job it can't download.
5. **Set `CONVT_SOURCE_URLS=1` on convt-api** only after every worker that can claim jobs runs the new image. Before rolling a worker back to an older image, unset it and wait until no queued or running `source_url` job is left: `select count(*) from cloud_jobs where source_url is not null and status in ('queued','running')`.
6. **Decide the account job limit.** Every job holds one of the account's 100 job slots (`jobs::MAX_STORED_JOBS`, from the P12 security review) for 24 hours, success included, so an API customer tops out at about 100 conversions a day. That is too low for API revenue. Set `CONVT_MAX_STORED_JOBS` on convt-api (size it from retained output, not the 50 GB declared-input budget: `source_url` jobs declare no input bytes, and each job can keep up to 4 GB of outputs for 24 hours, so the slot count is the real bound on stored output; start at 1,000 and raise it while watching bucket size), and update `apps/docs/content/reference/limits.mdx` and the `/api` page's note to match.
7. Check: `GET /ready` returns `{"status":"ready","database":true,"storage":true}`, `POST /v1/convert` converts a small PNG end to end with a real key, and a job with `webhook_url` delivers to a request bin.

`railway.json` for convt-api now gates deploys on `/ready` instead of `/health`, so a release that cannot reach Postgres or the bucket never takes traffic.

## Reliability

| Concern                                | Behavior now                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Liveness vs readiness                  | `/health` answers `ok` without touching anything. `/ready` checks Postgres (`select 1`) and storage (listing the configured bucket) with 3-second timeouts, and answers 503 while draining.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| API deploys and restarts (Railway)     | SIGTERM stops new connections and gives in-flight requests 24 seconds (`drainingSeconds` is 30). A waiting `POST /v1/convert` answers at once: `202` to JSON callers, `409 still_running` to file callers with an `Idempotency-Key`, and `504 timeout` (job cancelled, not charged) to file callers without one. The webhook dispatcher stops claiming.                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| Worker deploys and restarts (ms-a2)    | On SIGTERM a running conversion gets 20 seconds to finish. If it doesn't, the worker first puts the job back in the queue (`jobs::requeue`, fenced on its lease and attempt, without spending one of the 3 attempts), then stops the sandbox and deletes that attempt's outputs. The handoff gets 3 seconds and cleanup 4; if Postgres is too slow for the handoff, lease recovery retries the job at the cost of one attempt. A conversion that finishes during the grace period is settled before sandbox cleanup. Before this branch the job failed with `worker_shutdown`, and the customer had to start over after every deploy. Needs a stop timeout above 25 seconds (step 3).                                                                                                                            |
| Worker crash (SIGKILL, OOM, host loss) | Unchanged and still correct: the 30-second lease lapses, another worker claims the job with a higher `attempt`, and the stale worker's `finish` is fenced off. After 3 lost attempts the job fails with `expired_or_exhausted` and its reservation is released. Lease renewals time out after 2 seconds, so a slow database cannot hold the shutdown path for long.                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Spend-cap reservations                 | Released by finish, cancel, expiry and the exhaustion sweep, as before. Requeue keeps the reservation open because the job is still going to run. `/v1/convert` without an `Idempotency-Key` cancels its job when the client hangs up, so abandoned requests release theirs at once instead of at expiry. Cancellation is best effort: a job that already succeeded is billed.                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| Expiry sweep                           | Ran an `UPDATE` over every expired row every minute, forever, and turned cancelled jobs into `failed`. It now touches only rows that still hold a reservation or an unfinished status, and it clears `source_url` with the files.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Webhooks                               | Delivery state is on the job row. A pass claims up to 10 rows with `FOR UPDATE SKIP LOCKED` and a 120-second lease, sends them concurrently with a 22-second bound each, and fences every update on that lease, so two replicas never send the same claim. Delivery is still at least once: a receiver that answers after its 10-second timeout, or just before a process is killed, can get the event again, which is why events carry a stable `Convt-Event-Id`. On SIGTERM the dispatcher stops claiming and gets 4 seconds to record what it sent. `webhook_attempts` counts failed sends only, so a process that dies after claiming loses no attempt; the lease lapses and the row is claimed again. 8 sends, with waits of 10 s, 30 s, 2 min, 10 min, 30 min, 1 h and 1 h between them (2 h 42 min 40 s). |
| Memory                                 | `POST /v1/convert` bodies share a 512 MB budget per API process (`CONVT_INLINE_BUDGET_MB`). A request reserves its share from `Content-Length` before the body is read and releases it once the file is stored; past the budget it gets `503 server_busy`. The S3 client copies the body once more while uploading, so peak memory is about twice the budget: size the Railway service for at least 1.5 GB.                                                                                                                                                                                                                                                                                                                                                                                                      |

## Portability

Nothing in the API or worker depends on Railway APIs. What is Railway-shaped:

- **`PORT` and `CONVT_BIND_HOST`**: Railway injects `PORT`; any platform that does the same works.
- **`railway.json`**: replicas, restart policy, `drainingSeconds` and the healthcheck path. Fly.io (`fly.toml`: `kill_timeout = 30`, an HTTP check on `/ready`) and systemd or Docker on Hetzner (`stop_grace_period: 30s`, a healthcheck on `/ready`) take the same values.
- **Bucket lifecycle (required before launch)**: give the production bucket a rule that deletes objects older than 2 days. Upload URLs now expire at least a minute before their job, but a PUT accepted just before then can finish after expiry cleanup ran; the rule removes such strays, which the app no longer tracks. `crates/convt-worker/storage-dev.sh` sets a one-day rule on local MinIO the same way.
- **Object storage**: plain S3 (`S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `S3_REGION`, `S3_PATH_STYLE`). Railway Buckets, R2, Tigris, MinIO and AWS all fit. The API deletes each job's files at expiry (`routes::expire`), but the lifecycle rule above is still a deploy prerequisite: it catches uploads accepted just before their URL expired.
- **Postgres**: any Postgres 15+ with the roles from `packages/db/roles.sql`.
- **The worker sandbox** is the real constraint. The process backend needs root for setup, Landlock ABI 6, seccomp, writable delegated cgroup v2 controllers and private tmpfs mounts (`.agents/skills/test-convt-server/SKILL.md`). A Hetzner VM or a dedicated host gives all of that. Fly Machines are Firecracker VMs, so the gate should pass but must be run (`convt-worker --sandbox-gate` and `--sandbox-test`) before `CONVT_SANDBOX_VERIFIED=1` is set on the API. Do not move the worker to a platform where the gate fails.
- **Outbound network**: the worker now fetches `source_url` inputs and the API sends webhooks. Both go through `net_guard`, which refuses private, loopback, link-local, CGNAT, unique-local IPv6 and metadata addresses and pins the addresses it checked, and allows only port 443. If a platform routes egress through an HTTP proxy, note that the guard disables proxies on purpose.

## Free starter allowance: recommendation

Today a developer must subscribe to API billing in Polar and have a card seen (`subscriptions.card_seen_at`) before `createApiKey` lets them make a key, and `jobs::create` refuses API jobs without that subscription. That is the biggest drop-off between reading `/api` and a first successful call.

**Recommendation: 25 free conversions per account, lifetime, no card, `POST /v1/convert` only.** Changes needed, none of them in Polar:

1. **Database**: a `usage_events.kind` of `api_trial` (extend its check constraint), counted per user; or a `users.api_trial_remaining smallint default 25`. The usage-event route keeps the audit trail append-only and needs no new table.
2. **convt-server `jobs::create`**: when an API key's owner has no usable API subscription, allow the job if their `api_trial` count plus open trial reservations is below 25. Reserve 0 cents and record `api_trial` on success instead of `api_conversion`, so `meter::drain` never bills it. Refuse `source_url`, `webhook_url` and the 2 GB jobs routes for trial jobs, so the allowance can't be used for heavy video.
3. **`createApiKey`**: allow one key without enrollment; keep the 20-key limit for enrolled accounts.
4. **Dashboard**: show "N of 25 free conversions left" and the enrollment card when it reaches zero; the error for job 26 is `403 trial_exhausted` with a link to add a card.
5. **Abuse guard**: sign-in already needs a verified email or OAuth. Add a global daily ceiling on trial conversions (an env var, say 2,000 a day) so a signup farm can only burn a bounded amount of worker time, and alert when it trips.

Cost: 25 conversions of files under 25 MB is a few cents of worker time per account. Polar needs no product change. Leo's approval is needed because it is a pricing decision and adds a free tier, which AGENTS.md says not to add unasked.
