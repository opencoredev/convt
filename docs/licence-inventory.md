# Licence and codec patent inventory

This inventory records the checkout reviewed on 2026-10-05 for the Wednesday, 2026-10-07 launch. It covers the desktop payload, optional document pack, cloud services, SDK and website dependencies. It is not legal advice. A software licence grants copyright permissions; it does not establish that a codec's patents are licensed. Leo should have a lawyer review the distribution model and codec choices before selling the release.

Linux has an audited source and notice path. macOS and Windows have explicit gaps and must not inherit Linux's clearance. No public release, hosted source offer or patent licence was verified by this work. Packaging is changing concurrently, so freeze the release tree and repeat its audit before publication.

## Distribution and source obligations

convt's own code is AGPL-3.0-only. Charging for binaries, updates or hosted conversion is allowed, but recipients retain the licence's rights to modify and redistribute. Distributed binaries need their exact Corresponding Source, including applicable build scripts, modifications and dependencies. GPL and LGPL components need their own source and notices too. The release design supplies a matching source download alongside each binary, rather than relying on an informal promise to provide source later. If a written offer is used instead, counsel must check its recipients, duration and delivery conditions against the exact licence version. A link to an upstream repository alone is not necessarily the source for a patched shipped binary.

[AGPL section 13](https://www.gnu.org/licenses/agpl-3.0.html#section13) requires a modified network-interactive version to prominently offer its remote users an opportunity to obtain its Corresponding Source at no charge through a customary method. Treat convt-server, convt-worker and their deployed modifications as part of that review, together with the billing and website code that forms the service. Retain the source for the deployed revision and provide an accessible source offer to API users. The present server exposes health, formats, OpenAPI and jobs, but no dedicated source route was found. [The release procedure](release.md) requires source links from the server API, app About and download page; that requirement is not evidence that those consumers or a production source offer are complete. This is a launch obligation still to verify.

GPL source delivery must include the actual linked libraries and recipes, including statically linked components. LGPL shared libraries must remain replaceable, with notices and the required source or offer; a combined work may also require application object code or another suitable relinking mechanism, depending on how it is linked and the licence version. Do not prohibit reverse engineering needed to debug modified LGPL libraries. Signed applications and installers need a practical replacement/relinking review. Linux's private shared-library directory supports replacement, but layout alone does not prove all LGPL obligations. Product terms must preserve these rights.

The evidence is [Linux INVENTORY.md](../packaging/linux/INVENTORY.md), [license-components.lock.json](../packaging/linux/license-components.lock.json), [ffmpeg-static-components.lock.json](../packaging/linux/ffmpeg-static-components.lock.json), [native-notices.lock.json](../packaging/linux/native-notices.lock.json), [native-sources.lock.json](../packaging/release/native-sources.lock.json) and [the source publication procedure](release.md). An existing local `packaging/out/p11-closure-verified-a/0.1.0/source-audit.json` reports `distribution_ready=true` for `linux-x86_64` only. It certifies that frozen tree, not every current uncommitted file. Production publication needs a new matching `source-audit.json`, receipts, notices and source archive. The current evidence meets substantial Linux collection and build checks; live delivery and legal compliance remain unverified.

## Codec patents and paid distribution

H.264/AVC is implemented by x264 encoding and FFmpeg decoding. H.264 remains a patent-licensing question in relevant jurisdictions even though some older patents have expired. A paid software encoder/decoder may fall within product-licensing programmes; video distribution and broadcast licences are separate categories. Small volume may qualify for thresholds under a particular programme, but do not assume that a small paid app is exempt from every patent holder. Ask counsel about the exact product classification, territories, annual units and existing licences.

HEVC/H.265 is implemented by x265 encoding, FFmpeg decoding and libde265 decoding. HEIC stores HEVC-compressed still images, so libheif HEIC decoding and x265-backed HEIC encoding are part of this review too. There are multiple portfolios and programme terms; one pool or an x265 commercial copyright licence may not cover all required patent rights. Both encode and decode can matter. This is the most immediate codec question for a paid desktop release because convt deliberately distributes a software HEVC encoder and decoder on Linux and an encoder on macOS.

One option is to remove x265 from paid builds and from the libheif plugin set, then regenerate targets so software HEVC/HEIC output is not offered. Removing encoding alone does not clear bundled HEVC decoding. Another option is to implement and select macOS VideoToolbox and Windows Media Foundation HEVC encoding instead of distributing x265, and use OS HEIC facilities where available. VideoToolbox is compiled into the Mac FFmpeg replacement, but convt's video engine currently selects software x265; merely enabling VideoToolbox does not change the encoding path. Media Foundation and OS HEVC availability vary by Windows installation, extensions and device. Test feature detection and fallbacks, and ask counsel whether the OS vendor's grants cover convt's commercial use and distribution model. Linux could require a user-installed codec instead, with the legal effect reviewed separately. Do not silently substitute software x265 when the point of the change is to avoid bundling it.

AAC encoding and decoding use FFmpeg's native implementations, not a declared FDK-AAC dependency. AAC patent obligations depend on profile, implementation, jurisdiction and remaining claims; advanced profiles and extensions must not be treated as uniformly expired. Ask counsel whether the shipped AAC profile and software product require a licence. Copyright compliance for FFmpeg is independent of this question.

The commonly licensed historical MP3 patents have expired. LAME therefore presents a materially lower historical codec-patent concern than AVC or HEVC, while its LGPL copyright obligations remain. This statement is not a worldwide freedom-to-operate opinion about every implementation technique or later improvement.

AV1/AVIF use libaom on Linux; the Mac replacement adds dav1d for decoding. The [AOM patent licence](https://aomedia.org/license/patent-license/) and BSD notices are designed for royalty-free implementation of specified contributions. VP9 uses libvpx with [WebM's patent grant](https://www.webmproject.org/license/additional/). These grants do not promise immunity from every outside patent claim. Commercial third-party portfolios and AV1/VP9 claims should be checked for the intended territories and product, rather than treating either codec as legally risk-free. Retain patent-grant texts and review defensive termination conditions.

Leo should ask a lawyer to review: the AGPL network source offer and desktop terms; exact GPL/LGPL combinations and practical replacement on signed platforms; the unapproved Windows, Mac and document-pack closures; AVC and HEVC/HEIC encode and decode licensing for paid units in the countries of sale; AAC profiles; OS codec coverage; and current AV1/VP9 third-party claims. Compare the cost of a scoped codec licence with removing software encoders or restricting builds to OS codecs. No royalty schedule, exemption or indemnity is asserted here. This inventory supports that consultation and does not replace it.
